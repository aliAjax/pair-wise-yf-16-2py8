# 滑雪板调校店 · 本地协同台账

面向调校店两台平板同时维护同一张工单的场景。数据保存在浏览器 localStorage，
不依赖服务器，关页面/重启后可续作；两个浏览器标签页即可模拟两台平板实时协同。

## 解决的核心问题

- **互相盖掉改动**：每次保存生成一个变更批次（changeset），落盘前读取对端最新文档，
  按字段做三路合并（编辑基线 base / 台账现值 current / 本机新值 edit）：
  - 只有一方改了的字段直接并入；
  - 双方都改且结果不同的字段，谁都不覆盖谁，两个版本都保留在该字段上，
    在「待确认冲突」页由技师选定最终版本（仲裁本身也是一个批次，带留痕）。
- **可续作的本地台账**：工单、底板损伤、修补记录都是结构化文档，带全局修订号
  `rev` 与每个字段的写入者/时间/修订号；批次按 id 幂等，重复重放不产生重复数据。
- **损伤点稳定编号**：工单内 `D-001`、`D-002`… 保存时分配，重开/升级永不变；
  修补记录 `R-001`… 必须关联一个真实损伤点（新建同批次的损伤点通过临时编号重映射）。
- **确认作废与打蜡资格即时重算**：
  - 关联损伤点的类型/位置/尺寸/状态一旦改动，该损伤点下所有**已确认**修补立即作废
    （确认状态回退为否，备注写明作废原因）；
  - 修补**材料**改动同样立即作废旧确认；改技师/方式不影响；
  - 打蜡资格是派生结果：所有损伤点已修补且所有修补已确认（且无悬空关联）才可打蜡，
    作废后资格立刻变为不可用。
- **写盘失败不丢批次**：保存时批次先进入「未提交队列」（独立存储键），主台账写盘失败
  （配额/隐私模式/IO 异常）时批次完整保留，顶部黄条提示；每 15 秒、重新联网或点
  「立即重试写盘」时按序补齐，成功后才出队。
- **旧数据升级**：v1 自由文本台账（`底板划痕12cm…`、`待补P-Tex` 等）打开即升级：
  - 补发 ORD-/D-/R- 稳定编号，所有字段包装为带版本信息的 Tracked（标记“旧数据升级”）；
  - 从旧文本提取刃角、尺寸；旧修补按位置文字（含数字一致性校验）关联真实损伤点，
    单损伤且无位置线索的兜底关联，明确写错位置的绝不臆造（留空 + 原文保留）；
  - 原损伤文字存入 `legacyPosition`，旧修补原文存入 `legacyPosition`/备注，
    原有损伤和修复位置照旧可查；迁移的修补一律需重新确认。

## 目录结构

```
src/ledger/
  types.ts      数据模型、Tracked/Conflict、变更批次 op 定义
  merge.ts      三路字段合并、批次应用、确认作废、打蜡资格（纯函数核心）
  migrate.ts    v1 → v2 旧数据升级与结构补齐
  storage.ts    localStorage 持久化、未提交队列、重试、跨标签页同步
  seed.ts       首次打开的示例台账
  store.ts      React 状态层：编辑快照基线、草稿→批次、保存/仲裁
  ui-helpers.ts 冲突收集、标签、统计
src/components/
  OrderList.tsx     工单列表/筛选/打蜡资格标签
  OrderEditor.tsx   工单字段 + 底板损伤标记区 + 修补记录编辑
  ConflictPanel.tsx 字段冲突逐字段仲裁
```

## 本地运行

```bash
npm install
npm run dev        # http://localhost:62004
```

## 测试

```bash
npm test           # 59 项：编号/合并/冲突/作废重算/失败重试/旧数据升级
npm run typecheck
```

测试用内存 localStorage 桩跑完整的存储链路（esbuild 打包到 Node 执行）。

## 双平板演练方法

1. `npm run dev` 后开两个浏览器窗口（或同机两个标签页），顶栏各改一个设备名；
2. 两边打开同一工单，改**同一个字段**为不同值并分别保存 → 顶部出现待确认冲突，
   改**不同字段**则自动合并且双方刷新后互见；
3. 「批次记录」页勾选「模拟写盘失败」，在一端保存 → 出现未提交队列黄条；
   取消勾选后点「立即重试写盘」，批次补齐落盘。
